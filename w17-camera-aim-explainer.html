W17 · CB2 · Display-only explainer

How camera aim actually works today — and why the active path is locked

Two things move a camera command in this project. Only one of them is connected to a servo. The other one produces a number on a screen and stops. This page draws that separation literally, because the most important fact here is a negative, and prose buries negatives.

The negative, stated first

There is no iPhone → CRSF path, no iPhone → servo / gimbal / ESC path, and the firmware parses no iPhone data at all. There will not be one until a reviewed safety milestone says so.

Head tracking exists and runs. It is LOG-ONLY: validated, counted, classified, streamed to the ground station, and rendered as a chip. It never reaches a channel value. The overall FIRST_ACTIVE verdict is NO-GO / BLOCKED, and the protobuf enum that would have to carry an "active" state has no active value in it.

02 — STATE MACHINE

Nine enum values. None of them is "active".

Two sources feed one reported state: the receiver's lifecycle (is it running at all?) and the monitor's packet-derived classification. Receiver.State() returns fault first, then disabled, then delegates to the monitor.

UNSPECIFIED = 0 Never sent. A zero-value guard so a defaulted protobuf field cannot be mistaken for a real state. proto only · not emitted
DISABLED = 1 Receiver present but not running. In topology (a) the cmd wiring never produces this shape: with ingest on the receiver runs; with ingest off the broadcaster is nil and the RPC returns UNAVAILABLE instead. unit-tested · not observed live
FAULT = 2 Socket or config error. Observed live by starting a second mapper against an already-bound 5602 — the exclusive bind fails. receiver lifecycle
IDLE = 3 Running, no valid packet has ever arrived. packet-derived
INVALID = 4 Only invalid packets seen. Invalid packets bump counters and never replace the last valid packet. packet-derived
STALE = 5 Had a valid packet, then silence past the stale bound. Last-valid values are preserved separately for display. packet-derived · 300 ms
INACTIVE = 6 Fresh valid packet, but tracking_enabled = false. packet-derived
NOT_CENTERED = 7 Fresh, enabled, but not centered (or explicitly calibrated = false). packet-derived
ACTIVE_LOG_ONLY = 8 Fresh + enabled + centered. Everything the system can ask for is true — and it still produces no output. This is the ceiling. packet-derived · the top of the enum
The enum ends here

There is no value 9. HEAD_INTENT_STATE_ACTIVE_LOG_ONLY = 8 is the last line of the enum.

w17-mapper/pkg/proto/server.proto:527

This is the design's load-bearing detail, and it is the reason the ground-station chip can hardcode · NO CONTROL. There is no wire representation for "head tracking is aiming the camera", so no subscriber can render one, and no future value can appear without a proto change that trips the ground station's hermetic proto-drift guard (test/protoDrift.test.js) and the mapper's own .githooks/pre-push scan. ACTIVE_LOG_ONLY is the strongest state that exists, and it means "fully healthy, still doing nothing."

03 — TIMING

Two boundaries, 50 ms apart, doing different jobs

These get conflated constantly. They are not two opinions about the same number — one classifies for display and exists in code; the other would gate motion and exists only on paper.

300 ms — the log-only stale authority. Receive-time silence. 299 fresh / 300 fresh / 301 stale, test-proven. This is what decides STALE vs ACTIVE_LOG_ONLY and what the receiver and broadcaster already report. const DefaultStaleMs int64 = 300, pkg/headintent/packet.go:19. Ratified canonically at contract revision 84532ed §3. It supersedes the 400 ms figure that still appears in older readiness docs.
≤ 250 ms — the active freshness gate. Stricter, and it exists only in the U4 design (unlock plan §2.3.11.2 item 4). Head-derived motion would be permitted only while receive-time age ≤ 250 ms; 251 ms would run the failsafe decay. Its test row (B5: 249/250 permitted, 251 decay) is specified, not written. No code implements this today.
Why they differ, and why the gap is the point. Between 251 and 300 ms the diagnostic state can still read ACTIVE_LOG_ONLY while the future arbiter would already be decaying to centre. That is deliberate: the active gate must always be at least as strict as the log-only boundary and must never be relaxed past 300 ms. Classification is allowed to be more generous than motion; motion is never allowed to be more generous than classification.
Two more numbers that are not these two. The packet's own timeout_ms field (app default 250 ms, validated 1..5000) is an advisory diagnostic hint only and can never weaken the receiver threshold. Separately, the iPhone's local motion-sample freshness is Codex-owned: it was 500 ms, and the ratified requirement before any active use is that the sender stops emitting when its Core Motion sample is older than 250 ms. Those are two independent 250 ms guards — sender-side sample age and mapper-side receive age — and the mapper never trusts the iPhone's timestamp_ms for freshness. Receive time only.

04 — THE GATES

FIRST_ACTIVE: two flags, both off, both required

Neither flag alone does anything. This is not defence-in-depth decoration — the two mechanisms prove different things, which is why one of them was deleted from the design rather than kept as a fallback.

Gate 1 · compile-time

//go:build w17_first_active

A Go build tag, and only a build tag, absent by default. When absent the arbiter file is not compiled at all and the build links a passthrough stub — so the shipped default binary physically cannot produce head-derived motion. Assertable by symbol absence (go tool nm), not just by a runtime default.

AND
Gate 2 · runtime

W17_FIRST_ACTIVE_ARM
(working name)

Even inside a FIRST_ACTIVE build, an explicit runtime enable is required, default off, plus the per-tick armed precondition. Runtime-on inside a non-FIRST_ACTIVE build does nothing, because there is no active branch to reach.

Why the const alternative was deleted, not demoted. An earlier revision allowed gating via const firstActive = false as a linker-dropped dead branch. That silently disarms the shipped accident guard: w17-mapper/.githooks/pre-push scanned for exactly two literals — lowercase w17_first_active and the uppercase word FIRST_ACTIVE — and const firstActive = false matches neither, so arbiter code gated that way would have passed both checks and reached a public remote. The two mechanisms also prove different things: a build tag makes the branch absent; a const makes it eliminated — compiled, type-checked, and flippable by a one-character edit. Hence the naming contract: the tag must be lowercase w17_first_active exactly, because that is the literal the hook greps. Status note: the hook was extended to catch the const form in w17-mapper 432a809 (2026-08-04), which discharges the "owed" item recorded in unlock plan §2.3.11.4.
A weaker, separate gate sits below this one. -headtrack-ingest / W17_HEADTRACK_INGEST is also default-off, but it only gates the receiver. FIRST_ACTIVE is a second, stricter gate on the arbiter, and it stays off even when ingest is on. Ingest on + FIRST_ACTIVE off = exactly today's behaviour.

05 — WHAT WOULD CHANGE

If the gate ever opened, this is the shape of it

Recorded so the locked state is legible as a decision, not an omission. None of this exists in code. Deliberately no scaffolding was added either — even dead-ended shaping code would bake in constants and a control-path stage the review has not approved.

Where it would live

  • A single post-node-graph stage, between the eval loop's [16]CRSFValue and crsf.PackChannels — one auditable choke point, not nodes inside the user-editable mixer graph.
  • A pure function of (eval array, read-only diagnostics snapshot, arbiter memory, monotonic now).
  • It would touch only indices 8/9 and never write back into the receiver, monitor, broadcaster, or graph.

What would gate motion

  • All simultaneously, every tick: compile flag and runtime flag and armed and tracking_enabled and centred and fresh (≤ 250 ms).
  • Losing any one drops immediately into a rate-limited decay to commanded 992.
  • Right-stick-wins takeover is global across both axes, latches, and never auto-restores.

The rule that is easiest to break

  • Arm / deadman / override state must not be read from the [16]CRSFValue array.
  • That array carries hold-last semantics, so a value read from it cannot distinguish "the operator is holding this" from "the input device is gone."
  • Device-absent must be an affirmative disarm (invariant I10, demonstrated by physical unplug under R15) — not an absence of evidence.
Commanded, never measured. There is no gimbal position feedback anywhere in this system — not in firmware telemetry, not on the CRSF uplink, not on the bridge. So every pan/tilt number this project displays or exports is a command, "near limit" means command saturation rather than confirmed mechanical contact, and CRSF 992 is an authoritative commanded centre whose physical safety still needs bench validation. The ground station honours this: the camera dot is violet observed stick input, the Head Tracking card is LOCKED, and ACTIVE AUTHORITY reads NOT REPORTED BY MAPPER rather than being fabricated from what the browser can see.
